## 1. 问题陈述（实验场视角）

1. **audit 是最后一个未实战的核心组件**：六轮「晚一步启用」后，「文档与代码持续对齐」始终无机器检查；五个版本叠加的 spec（共识 v1→v5 同文档共存、architecture.md 停在 v1、数据模型 34 节含已被取代段落）漂移风险已实际累积
2. **技术债承诺到期**：`world.player` 别名 getter 在 R5 设计文档白纸黑字「R6 清理候选」
3. **流程闭环缺最后一环**：spec→门禁→骨架→实现→验收→（缺 audit）→fix 分流——补上即全环贯通

## 2. 需求清单

### F-R6-1 启用 /audit 并跑首轮全量审查（P0）

- 从 standard 安装 audit skill + 配置输入映射（写入 CLAUDE.md「Audit 输入映射」段）
- 按本项目实情裁剪 phase：**spec**（共识自身质量/TBD 收敛/追溯链）、**architecture**（共识→架构对齐）、**behavior**（验收条件→测试覆盖对齐）、**数据模型对照**（文档 ↔ 代码契约，如碰撞矩阵/常量表/状态机）；无后端 API 与第三方集成，api/integration phase 裁剪并声明
- 产出：审查报告（immutable）+ findings-registry 首批条目（proposed 状态入库）
- audit 纪律红线：**只记录不修**（task-lifecycle 探索期可见执行）

### F-R6-2 findings 消化（P0 附带）

- 对 findings 走分流：纯文档勘误直接修 / 代码或语义类走 issue 流程（复用 #6~#8 验证过的全链路）/ 噪音 dismissed 留 reason
- registry 状态机完整流转（proposed → confirmed/dismissed → resolved）

### F-R6-3 别名 getter 清理（P1，audit 后执行）

- 移除 `world.player` 别名与默认参兼容层，全量改写为 `players[]` 显式调用
- **这是一次有意的「大规模合法基线修订」实验**：预计触及基线测试 50+ 处——修订纪律（独立 commit/逐条依据/diff 可验）在高修订量下的可执行性，是 R5「零修订」样本的对照组
- `[OPEN-R6-1]` 修订粒度：逐文件 commit vs 单 commit 全量（dogfood 角度逐文件信息量更大，成本也更高）

## 3. 明确不做（本轮）

2P 无尽与成就（**R7 候选，绑定条件：用写入点级粒度纪律重列模式分叉清单后实施**）/ 双人对战 / 移动端 / 联机 / 编辑器 / 随机地图。

## 4. 成功指标（实验场口径）

- audit 首轮：报告落盘 + findings 全部入 registry 且每条有终态（无悬挂 proposed）
- 噪音率（dismissed/总数）与命中率（confirmed 且引发改动/总数）如实记录——这是 audit 价值评估的核心 dogfood 数据
- 清债后：基线全绿 + 别名零残留（grep 可验）+ 修订全程留痕
- 轮末 dogfood 增量反哺（audit 首跑样本 + 大规模修订样本）
